# Payment integrity

- Dodo immediate orders, bundle applications and webhook leases are service-only durable state; apply_dodo_bundle locks the order and calls record_pull atomically with unique payment/order guards and no wallet entries. Legacy wallet orders are refused. Why: concurrent deliveries must not duplicate pulls or create balances.
- Dodo pull baskets are created by create_dodo_basket and applied only by apply_dodo_basket, which re-checks Dodo-read facts and metadata against stored lines and calls record_pull per line in one locked transaction; integrity failures mark needs_review with nothing applied, inactive matchups become a single durable partial refund. Why: hostile metadata or crashes can never apply part of, or more than, what was paid.
- Refund POSTs are claimed durably once; uncertain outcomes require reconciliation and are never blindly retried because Dodo refund idempotency is undocumented. Why: avoid duplicate refunds.
- Recovery tokens travel only in URL fragments and request bodies; browser storage is environment-scoped and the database stores only SHA-256 hashes. Why: wallet links are bearer credentials.
- Legacy Stripe modules remain disconnected and their webhook is disabled until real Dodo sandbox verification permits deletion. Why: preserve the requested staged migration without allowing legacy writes.
- PayGlocal orders and matching immediate credit/debit entries are service-only; apply_payglocal_payment calls record_pull inside one locked SQL transaction with unique order/gid guards and zero carryover. Why: concurrent or replayed callbacks cannot duplicate pulls or partially apply a bundle.
- PayGlocal callbacks verify RS256 with the environment PUBCERT and merchant identity; incomplete/unverified callbacks use only the stored gid/merchant ID for authenticated Get Status. Why: browser redirects and decoded claims are never payment proof.
- PayGlocal request JWS signs the official digest-object format over exact body bytes; returned status URLs stay on the selected API origin and hosted redirects stay under payglocal.in. Why: preserve protocol integrity and prevent credential forwarding.
- Dodo buyer email is read only from the verified Dodo payment (customer.email) for the matching order/environment/checkout, stored best-effort first-write-wins outside the fulfilment transaction, and dodo_orders stays service-only (no anon/authenticated grants). Why: the email must never be publicly readable and capture must never affect fulfilment.
- The post-payment screen trusts only the stored order: it checks with gradual backoff until paid/failed/expired/refunded/needs_review, treats read errors as still confirming, and checkout-window events can only prompt an earlier check (restarting the short gaps but never the give-up deadline), never undo an end state; a close with no earlier sign of payment is worded as cancelled and stops silently after a short window instead of the calm note, while buyer dismissal only hides waiting notes and never stops checking or hides a receipt; the Dodo overlay is closed by us when it hands control back (manualRedirect). Why: a confirmed payment must never look pending or failed.
- Buyer receipts and refund notices load the order only from RECEIPT_ORDER_TABLE[provider] (app-email.server), and each provider's fulfilment calls sendPurchaseNotices with its own provider id after releasing the order lease; pull lines come from the same dodoReceipt builder as the confirmation screen. Why: a wrong-table read returns empty instead of erroring, which once silently stopped every Dodo receipt.
- Receipt links point each applied line at its public /pull/$id page only when loadPullCard can draw that pull now, else its public matchup page, else home; hrefs carry only public pull ids or slugs. Why: forwarded receipts must never break or expose order, payment or contact identifiers.
